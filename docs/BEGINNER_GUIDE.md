# 从零理解 Galbot 折衣部署优化

这篇文档写给第一次接触机器人推理部署、网络通信和控制滤波的读者。先不看代码，也不要求懂控制理论。我们从“机器人为什么慢、为什么抖、为什么来回摆”开始，再逐步解释每一版代码为什么出现。

## 1. 整套系统到底在做什么

可以把机器人想成一个人：

- 四个相机是四只眼睛。
- 关节状态是手臂当前弯曲角度。
- 客户端是现场助手，负责拍照、记录关节、发送信息、执行动作。
- 服务端模型是远程大脑，负责看图并预测接下来怎么动。
- WebSocket 是现场助手和远程大脑之间的一条电话线。

一次完整循环是：

```text
四路相机拍照 + 读取关节
             |
             v
客户端整理 obs_horizon 段历史
             |
             v
通过 WebSocket 发给服务端
             |
             v
模型预测一段 action chunk
             |
             v
客户端逐点发送给机器人关节
             |
             v
重新观察，再进行下一轮
```

模型不是只回答“下一步怎么动”，而是一次给出一串动作。例如返回 16 步：

```text
第 0 步 -> 第 1 步 -> ... -> 第 15 步
```

这一串动作就叫 action chunk。

## 2. 三个最重要的词

### obs_horizon

`obs_horizon` 是模型一次要看多少个历史时刻。

例如 `obs_horizon=4`，四个相机每个保留 4 帧：

```text
头左相机: t-3, t-2, t-1, t
头右相机: t-3, t-2, t-1, t
左臂相机: t-3, t-2, t-1, t
右臂相机: t-3, t-2, t-1, t
```

总图片数是：

```text
4 个相机 x obs_horizon
```

这个数量不能为了省流量随意减少，因为它是模型输入结构的一部分。

### action chunk

模型一次预测的一段未来动作。当前服务端最多返回 16 步，每步包含：

```text
左臂 7 个关节 + 右臂 7 个关节 + 左夹爪 + 右夹爪 = 16 维
```

### 30 Hz

30 Hz 表示理论上每秒执行 30 个动作点，每个点相隔约：

```text
1 / 30 秒 = 33.3 毫秒
```

若 16 步全部执行，持续时间约：

```text
16 / 30 = 0.533 秒
```

## 3. 第一阶段：为什么通信会达到几秒

### 原始做法

原始路径可能把相机图像解码成完整 RGB 数组后再发送。

一张 `640 x 480` RGB 图片的理论大小是：

```text
640 x 480 x 3 = 921,600 bytes
约 0.88 MiB
```

假设 `obs_horizon=4`：

```text
4 个相机 x 4 帧 x 0.88 MiB
= 14.1 MiB
```

这还没有算 MessagePack 容器、Python 对象、内存复制和 TCP/WebSocket 开销。

### 形象例子

模型只需要看一张身份证大小的照片，但原始系统每次都把整张海报邮寄过去；服务端收到海报后，才把它裁成身份证大小。

网络慢的不只是“邮寄过程”：

- 客户端要展开 RGB 数组。
- MessagePack 要遍历和打包大量像素。
- 内存中要复制大块数据。
- 服务端要接收和反序列化。
- 服务端最后仍会缩放到 `224 x 224`。

### v01 的思路

既然模型最终只使用 `224 x 224`，客户端先缩小，再 JPEG 压缩：

```text
相机帧 -> 224x224 -> JPEG quality 75 -> bytes -> WebSocket
```

一张 `224 x 224` 原始 RGB 是：

```text
224 x 224 x 3 = 150,528 bytes
```

JPEG 后常见可能是 8 KB 到 30 KB。实际大小取决于画面纹理和噪声。

### 为什么不用 Base64

可以把二进制 JPEG 想成一箱货物。MessagePack 本身就允许直接运输这箱货物。

Base64 相当于为了用只能写文字的表格运输货物，先把货物拆成字符。每 3 个原始字节通常变成 4 个字符：

```text
4 / 3 = 1.333...
```

因此理想情况下多约 33.3%，还增加一次编码和解码。

#### 原文证据

RFC 4648 Section 4 原文：

> “24-bit groups of input bits as output strings of 4 encoded characters.”

翻译：24 bit 输入组会表示为 4 个编码字符。24 bit 是 3 字节，因此完整编码组是 3 字节变 4 字符，这就是 `4/3` 的来源。

MessagePack 规范对 Binary 的定义是：

> “represents a byte array”

翻译：Binary 表示字节数组。当前协议既然能直接传 byte array，就没有必要再把 JPEG 包装成 Base64 文本。

原文、链接和适用边界见 `QUOTED_EVIDENCE.md` 第 1、2 节。

### v01 为什么能 work

模型输入结构没有变化：

- 图片数量不变。
- `obs_horizon` 不变。
- 相机顺序不变。
- 状态 shape 不变。
- 服务端仍把 JPEG 解码回 RGB 再交给模型。

改变的是运输方式，不是模型看见的数据结构。

### v01 为什么仍然会抖

通信变快不代表控制循环就连续。客户端仍可能在执行动作时停下来采集整段历史，所以接下来出现 v02。

另外，原始服务端默认同步执行 `np.savez_compressed()`。NumPy 官方原文是：

> “Save several arrays into a single file in compressed .npz format.”

并说明：

> “The .npz file format is a zipped archive”

因此它明确包含压缩归档和文件写入。关闭默认 debug 落盘能把这部分移出响应关键路径，但具体节省多少必须实测。

## 4. 第二阶段：为什么机器人会“走一下，停一下”

### 原始控制时间线

假设 30 Hz，每 33 ms 应该发一次关节目标：

```text
正常: 命令 命令 命令 命令 命令
时间:  0   33   66   99  132 ms
```

但原始代码会在 chunk 中途调用 `capture_observation_history()`。如果 `obs_horizon=4`，它会连续采 4 个时刻，并在中间 sleep：

```text
命令 命令 [拍照 + 等待 + 拍照 + 等待 + 拍照 + 等待 + 拍照] 命令
```

控制线程在方括号期间不能继续发送关节命令。

### 形象例子

一个鼓手本应均匀地敲：

```text
咚 咚 咚 咚 咚 咚
```

但他每敲几下就停下来拍四张照片：

```text
咚 咚 咚 ...... 咚 咚 咚 ...... 
```

机器人收到的运动节拍也会变得不均匀。

### v02 的后台观测

v02 把工作分给两个人：

```text
控制线程:    只负责按节拍发送关节目标
观测线程:    持续拍照、压缩、维护 obs_horizon
```

观测线程始终保留最新的完整历史。控制线程需要推理时，只取一份 snapshot。

#### 原文证据

Python `threading` 官方文档原文：

> “Threads are particularly useful when tasks are I/O bound”

翻译：当任务主要受 I/O 等待限制时，线程特别有用。相机读取和等待外部设备属于适合后台化的类型。

注意：这句话支持“线程适合等待型任务”，但不能证明 Galbot SDK 的相机和关节 API 一定线程安全；这一点仍需设备测试。

### 为什么必须用完整 snapshot

不能一边复制历史，一边让后台线程修改它，否则可能出现：

```text
前三张图来自时刻 A
最后一张图来自时刻 B
state 又来自时刻 C
```

所以代码用锁保护历史更新和 snapshot，保证一次请求看到的是一套一致数据。

### chunk 边界为什么会跳

假设上一段最后一个关节目标是：

```text
q_old = 0.50 rad
```

新 chunk 第一条却是：

```text
q_new = 0.30 rad
```

直接切换相当于一个周期要求关节变化 `-0.20 rad`。

v02 用 3 步渐变：

```text
0.50 -> 0.40 -> 0.30 -> 继续模型轨迹
```

就像汽车换道时沿曲线过去，而不是瞬间横移。

### v02 为什么能 work

- 相机处理不再直接阻塞命令下发。
- 新 chunk 从当前姿态逐渐接入。
- `obs_horizon` 仍完整维护。

### v02 为什么还不够

它只能解决控制空窗和 chunk 首帧跳变。如果一个 chunk 内部本身就是：

```text
0.40, 0.44, 0.39, 0.45, 0.38
```

机器人仍会在 chunk 内来回摆，于是需要 v03。

## 5. 第三阶段：为什么 chunk 内会小幅抖动

### 什么叫高频变化

假设模型给一个关节的目标：

```text
0.40, 0.44, 0.39, 0.45, 0.38
```

方向不断改变：

```text
向正 -> 向负 -> 向正 -> 向负
```

即使每次变化不大，30 Hz 连续执行时也会看起来像细小抖动。

### v03 第一层：整段 5 点平滑

不要只相信当前一个点，而是参考前后几个点。

生活例子：五个人分别估计桌子位置，一个人说偏左，一个人说偏右。取加权平均比完全听某一个人更稳定。

简化例子：

```text
原始: 0.40, 0.44, 0.39, 0.45, 0.38
平滑: 0.41, 0.41, 0.42, 0.41, 0.40
```

实际代码使用对称三角权重，不是简单算术平均。

### v03 第二层：在线低通

公式：

```text
新下发 = 上次下发 + alpha x (模型目标 - 上次下发)
```

默认 `alpha=0.25`。

假设上次下发 `0.40`，模型突然要求 `0.60`：

```text
差值 = 0.20
本次只走 25% = 0.05
新下发 = 0.45
```

下一周期若模型仍要求 `0.60`：

```text
新下发 = 0.45 + 0.25 x 0.15 = 0.4875
```

它会逐渐靠近，而不是瞬间跳过去。

### v03 第三层：单步限幅

即使滤波后仍变化太大，也规定每周期最多变化 `0.02 rad`：

```text
想从 0.40 去 0.60
第 1 步最多到 0.42
第 2 步最多到 0.44
...
```

这叫 slew-rate limiting，可以理解为给目标变化设置“限速牌”。

### 为什么默认不设手臂死区

死区是“小于某个变化就完全不动”。它可能造成：

```text
小误差 -> 不动
小误差继续积累 -> 仍不动
超过阈值 -> 突然动一下
```

这可能形成粘住后突然释放的小跳，所以默认 `arm_deadband_rad=0`，主要依靠连续低通。

### v03 为什么能 work

三个处理层分别负责：

```text
整段平滑: 去掉 chunk 内快速正负交替
在线低通: 保证实际下发连续
单步限幅: 限制最坏单周期变化
```

### v03 为什么仍可能来回大摆

低通只能把错误轨迹变慢、变小。如果模型每轮都重新生成同一段 A 到 D，机器人仍可能不断 A-D-A-D，只是没那么剧烈。因此出现 v04。

#### ACT 论文如何描述朴素 chunk 的问题

ACT 原论文原文：

> “A naïve implementation of action chunking can be sub-optimal”

并紧接着写道：

> “can result in jerky robot motion.”

翻译：朴素的 action chunk 实现可能不是最优，并可能造成机器人动作不顺滑。

这说明 chunk 离散切换本身就是论文明确讨论的问题。但它不能单独证明当前视频只有这一种原因，底层位置控制、模型重复轨迹和接口时序也要测量。

## 6. 第四阶段：为什么严格同步仍会反方向往返

### 先纠正一个容易误解的说法

如果确实是“执行结束后才发新状态”，就不能简单说成异步旧状态导致反向纠正。

严格同步下更可能的问题是：新旧 chunk 没有连续性约束。

### 用一个具体例子理解

模型第一次预测：

```text
chunk 1: A -> B -> C -> D
```

机器人执行完，已经在 D 附近。

但衣服变化不明显，或者模型不能准确判断任务阶段。下一次它又输出一段相似动作：

```text
chunk 2: A' -> B' -> C' -> D'
```

问题是 `A'` 可能接近上一轮的 A，而不是当前的 D。于是：

```text
D -> A'   先反方向回去
A' -> D'  再正方向走回来
```

下一轮再次重复，就形成视频里的周期往返。

### 为什么模型可能重复一段动作

可能因素包括：

- 请求中 `history_action=None`，没有显式告诉模型上一段执行了什么。
- 视觉上衣服变化很小，连续两次输入很相似。
- 模型输出的是绝对关节目标，新 chunk 第一条不保证等于当前关节。
- 固定 diffusion seed 会让相似输入更稳定地产生相似模式。
- 训练损失通常监督每个 chunk 是否像示范，不天然保证两次独立推理首尾相接。

这些是需要日志验证的工作假设，不代表只凭视频就能确定唯一原因。

ACT 论文对 action 的定义提供了一个重要背景：

> “An action here corresponds to the target joint positions for both arms”

翻译：这里的 action 对应双臂目标关节位置。

如果本项目 checkpoint 也采用绝对目标关节位置，那么新 chunk 第一条与当前反馈不连续时，会直接要求机器人回到另一个姿态。当前项目还需要通过模型配置和归一化定义确认它与 ACT 原实现是否完全一致。

### v04 第一招：只执行前 4 步

模型仍返回 16 步，但客户端默认只执行前 4 步：

```text
返回:  [0 1 2 3 4 5 ... 15]
执行:  [0 1 2 3]
重新观察并推理
```

30 Hz 下：

```text
执行 16 步 = 0.533 秒
执行  4 步 = 0.133 秒
```

形象地说：导航给了未来 500 米路线，但机器人只先走 100 米，就重新看路，而不是闭着眼走完 500 米。

这与 receding-horizon control 的思想相似：只执行计划的一小部分，再根据新状态重新规划。

### v04 第二招：从真实关节状态接入

收到新 chunk 后，不把上一段计划值当成机器人实际位置，而是读取真实反馈：

```text
q_start = latest_feedback
```

然后从这个真实起点做边界混合。

### v04 第三招：反向确认

如果一个关节刚才一直向正方向运动，新目标突然要求反向：

```text
第 1 次反向: 先不执行
第 2 次反向: 仍不执行
第 3 次反向: 确认模型确实持续要求反向，允许执行
```

这类似按键消抖：按钮因为金属弹片会短暂开关多次，程序要求信号持续稳定后才承认真的按下。

只有误差超过 `0.004 rad` 才进行反向确认，避免把极小数值噪声当成真实方向变化。

### 为什么反向确认不能无限强

折衣任务本来就可能需要真正反向。如果永远禁止掉头，机器人也无法完成动作。

所以它只是过滤短暂反向，不是锁死方向。确认步数越大：

- 越不容易抖。
- 真正需要反向时越迟钝。

### v04 为什么能 work

- 错误 chunk 最多只执行较短一段，最大错误位移下降。
- 每轮用更新后的衣物和关节状态重新推理。
- 新 chunk 从真实反馈衔接。
- 偶发反向预测不会立刻触发掉头。

### v04 仍不能保证什么

- 模型连续稳定地要求反向时，系统最终仍会允许反向。
- 如果模型不断重复同一段前 4 步，机器人可能原地重复局部动作。
- 推理很慢时，严格同步会在两段之间保持最后目标，出现停顿。
- 当前没有完整实现 ACT temporal action ensemble。
- 当前没有把已执行 action 作为 `history_action` 输入模型。

## 7. Temporal action ensemble 是什么

模型在不同时间会对同一个未来执行时刻做出多次预测。Temporal ensemble 不只采用最新 chunk 的一个点，而是融合多个历史 chunk 对该时刻的预测。

形象例子：

```text
昨天的天气预报说今天 25 度
今天早上的预报说今天 27 度
刚刚的预报说今天 26 度
```

与其只相信其中一次，可以按新旧程度加权融合。

ACT 原工作使用 temporal aggregation 改善 action chunk 之间的平滑性。当前 v04 的短视界、边界平滑和反向确认是较简单的部署保护，不等同于完整 temporal ensemble。

#### 论文原文中的关键区别

ACT 论文原文：

> “we aggregate actions predicted for the same timestep.”

翻译：他们融合的是针对同一个执行时刻预测出来的多个 action。

因此：

```text
普通低通:
融合相邻执行时刻的 action

Temporal ensemble:
融合不同推理请求对同一执行时刻的 action 预测
```

论文还明确写道，他们的方法不同于把当前 action 与相邻 timestep action 聚合的普通 smoothing。这个区别非常重要：v03 的平滑能够减小 chunk 内噪声，但不能替代跨 chunk temporal ensemble。

## 8. 如何判断现在是哪一种问题

### 通信很慢，但机器人执行时还算连续

先比较 v00 与 v01：

- 请求有多少 MB？
- JPEG 后下降多少？
- 服务端是否仍默认写 debug 文件？

### 每执行一段就明显停一下

重点检查 v02：

- 相机和 JPEG 是否在控制线程完成？
- `set_joint_commands()` 最大间隔是多少？

### 一段 chunk 内快速小幅左右抖

重点检查 v03：

- raw action 相邻点是否正负交替？
- 平滑后 `max(abs(diff()))` 是否下降？
- 真实反馈是否跟随命令抖动？

### 每隔约一个 chunk 大幅往返

重点检查 v04：

- 新 chunk 第一条离当前反馈有多远？
- 相邻 chunk 总体运动方向是否相反？
- 改成只执行 4 步或 2 步后，摆动幅度是否下降？

### 命令很平滑，但真实机器人仍抖

这时问题可能在底层：

- 位置控制增益过高。
- 负载、摩擦或机械间隙。
- `set_joint_commands` 的时长参数使用不当。
- SDK 每次调用都会重置轨迹规划器。
- 真实反馈噪声或关节控制器振荡。

需要 Galbot SDK 的接口定义和底层日志，单靠客户端滤波不能证明或根治。

## 9. 推荐的新手测试顺序

不要一次打开所有优化后只看结果，因为出问题时不知道是哪层造成的。

1. 用 v00 记录原始请求大小、RTT、控制间隔和摆动幅度。
2. 换 v01，只确认通信是否显著下降。
3. 换 v02，只确认长控制空窗是否消失。
4. 换 v03，确认 chunk 内小抖是否下降且动作没有过慢。
5. 换 v04，确认跨 chunk 大幅往返是否下降。

每次保持：

- 同一件衣服和摆放位置。
- 同一机器人初始姿态。
- 同一 checkpoint。
- 同一 `obs_horizon`。
- 同一相机位置与光照。

## 10. 当前 v04 默认参数怎么理解

```bash
--hz 30
--command_hz 30
--transport_image_size 224
--transport_jpeg_quality 75
--sync_execute_steps 4
--chunk_smoothing_window 5
--chunk_blend_steps 3
--arm_filter_alpha 0.25
--max_arm_step_rad 0.02
--arm_deadband_rad 0
--reverse_confirm_steps 3
--reverse_threshold_rad 0.004
```

- `sync_execute_steps` 越小：重新观察越频繁，但推理停顿占比可能变大。
- `chunk_smoothing_window` 越大：整段越平滑，但动作细节越容易被磨掉。
- `arm_filter_alpha` 越小：越平滑，但延迟越大。
- `max_arm_step_rad` 越小：动作越慢，单周期冲击越小。
- `reverse_confirm_steps` 越大：越不容易掉头，但真实反向越迟。

## 11. 一句话总结每一版

```text
v00: 先保留原始问题，建立基线。
v01: 不寄海报，只寄模型真正需要大小的压缩照片。
v02: 拍照交给后台，不让控制线程停下来；换 chunk 时平滑接轨。
v03: 对 chunk 内动作去噪、低通并限速。
v04: 不盲目执行完整长轨迹，走一小段就重新看路，并过滤短暂反向。
```
